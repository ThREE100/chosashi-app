# 毎朝ドリル（択一）解説記事の作成プロンプト

毎朝ドリルの択一（朝）の解説記事（note用）を作るときの、**執筆ルールの正本**。記事を1本作るたびに、末尾の「PDCAの手順」を回して、このプロンプトとチェッカー（`check_kaisetsu.py`）を自動的に改良する。

## 1. 目的と読者

- 目的：用語や制度になじみのない**初学者**が、条文の言葉と実際の場面を結びつけてイメージできるようにする。
- 丸暗記ではなく、「その人は、どんな場面で、どんな立場か」を具体例で示す。条文の読み方（「又は」「及び」の解説など）の説明はしない。
- 記事は対外発信（note）に使う。自分だけが知っていればよいこと（内部のファイル名、道具の名前、「原文で照合済み」の記載、個人の演習結果）は、記事にもプロンプトにも書かない。

## 2. 入力と出力

- 入力：`morning/problems/AM-NNN.json`（問題文・各肢の正誤・根拠条文）。条文は `note-articles/laws/` の原文で確かめる。確かめられない点は、確認事項ブロックに分けて書く。
- 出力：`kaisetsu/dayNNN-am-kaisetsu.md`（NNNは3桁）。画像は生成せず、プロンプトまで。
- 作り方：`src/dayNNN.py` に記事のデータ（文章・図解の文言）を書き、`python3 build_kaisetsu.py N` で組み立てる（図解プロンプトの共通部分は `src/tpl.py`）。Day004は手書きの見本で、組み立ての対象にしない。

## 3. タイトル（2026-10-27 決定）

```
## 【土地家屋調査士受験生向け】毎朝ドリル_Day004_択一解説～キャッチ～
```

- `Day` のあとは3桁。`～` は全角で前後にそろえる。キャッチは25字以内、体言止めかです・ます調（例：登記権利者は買主、登記義務者は売主）。
- 出題行は `**出題：毎日ドリル　第N日（朝）　択一**`。ドリルはオリジナル問題なので、年度・午前午後の部は書かず、noteの引用の出典欄は空欄にする。

## 4. 記事の構成（この順番）

1. タイトル → 出題行
2. 問題文の引用（`>`ブロック。行末は半角スペース2つ、肢の間は `>　  `、最後は選択肢の行）→ `---`
3. 導入文（2〜3文）：何の問題か、この記事で何を確かめるか
4. 各肢の解説 `### ア：結論を表すフレーズ`
   - 結論＋条文番号 → 「本肢は正しいといえます／誤りです」→ `**たとえば**、`で始まる具体例。
   - 誤りの肢は、問題文のどこが条文と違うかを一文で指摘する。
5. `---` → `### まとめ`（`- **ア（正）** …` の5項目）→ 一言 → `**正解：…の組合せ（選択肢N番）**`（まとめより前に正解を出さない）
6. 補足説明（誤りの肢のうち、混同しやすいもの。`### 補足説明（ウ）：…`）。表・時系列・対比にできる内容を選ぶ。
7. `---` → 確認事項ブロック（このまま使える点／使う前に確認したい点）
8. 見出し画像用フレーズ（肢の数＝5）→ 見出し画像プロンプト（女性のMC1人。トリ先生・藍子は入れない）
9. インフォグラフィック プロンプト（問題全体）：②型。2列・5枚のカード、番号なし、絵の中の文字は `Words allowed` の語だけ
10. インフォグラフィック プロンプト（◯肢・間違いノート）：補足説明をつけたら必須。④型。1つの補足に1枚を目安にする

## 5. 書き方のルール

- 敬体（です・ます）。肢は「ア」と単独で表記する。括弧は全角。
- 判例・先例・専門誌の番号は本文に書かない（条文番号は書く）。
- 1段落は約125字以内。長いときは段落を分ける。
- 具体例は、初学者が想像できる日常の場面（売買、新築、境界の揉め事など）にする。条文にない事実（精度の違い、制度の経緯など）を断定しない。一般的な整理は、確認事項ブロックで「条文からの一般的な整理」と分けて書く。
- 「たとえば」の具体例は、肢ごとに必ず入れる。補足説明にも入れる。
- 禁止語：決定木・判定木・ツリー（「判定の流れ」と書く）。

- **誤りを選ぶ問題で条文どおりの肢**は「本肢は正しいといえます」ではなく「条文のとおりで、正しい記述です」と書く（選ぶ対象と紛らわしくならないように）。まとめの後の一言は、選ぶ対象（誤り／正しい）を述べてから傾向を書く。
- **noteはMarkdownの表を表示できない**。補足説明の比較は箇条書きで書く（`build_kaisetsu.py` が表を箇条書きに自動変換するが、表は図解④の中で表現するのが本来）。
- **条文と実務にまたがる肢**は、本文には条文から言える結論を書き、実務の取扱い・先例・判例でしか言えない点は確認事項に「一般的な整理」「原文は未確認」と分けて書く。確認事項にも内部のファイル名は書かず、「過去問の解説記事の結論と照らして確認」のように言い換える。
- 具体例の数字（面積・金額・縮尺・期間）は仮定の数字であることを確認事項に書く。条文にない理由づけ（なぜそう定められたか）は足さない。
- キャッチに「常に」「必ず」は使わない（断定になりやすい）。

## 6. 図解プロンプトのルール

- 共通の雛形は `src/tpl.py`。見出し画像は1280×670、図解は1080×1920。
- 絵の中に入れる文字は、指定した語だけ（`ILLUSTRATION TEXT RULE`）。②のカードは `Words allowed inside this illustration` の行をつける。語がないカードは「（なし。…）」とする。
- ②のカードに番号を付けない（`NO NUMBERING`）。チェックマークは緑、バツは赤。②は「正しい決まりだけ」を描き、バツは使わない。
- ④で正反対の印（緑のチェックと赤のバツ）を並べるときは、IMPORTANTで「見出しの語が違う文字列である」ことを明記し、似た文字列は別の色で描かせる。
- 「特に注意する漢字」のリストは、そのプロンプトの本文に実在する漢字だけにする（機械チェックあり）。リストが「・」でつながる語（例：地目・地積）を本文に書くと誤検出されるので、「地目と地積」のように書く。
- 簡体字・繁体字の禁止、不透明な背景の指定は、雛形のとおり入れる。
- チェッカーは「・」でつないだ**3字以上**の漢字の並びだけを注意漢字リストとみなす。「居宅・店舗」「条・準則」のような2字の語は誤検出されないが、`sub`・`footer`・列見出しには、「規則と準則」のように「と」「、」でつなぐほうが安全。注意漢字は、本文に実在する漢字だけにする（見出し・タグ・語・列名から自動で拾う小関数を `dayNNN.py` の先頭に置いてよい）。
- 絵に入れる語（Words allowed）にラテン文字（A・B・Cなど）を入れない（「先の売買」「後の売買」のように日本語にする）。条番号などの算用数字は可。
- 「できない」ルールは、バツ印を使わず、南京錠と灰色の矢印で表す。抹消の記号や取り消し線は「細い横線（バツ形ではない）」と指定する。
- ②のカードは肢アイウエオの順で1対1に対応させ、A列・B列は肢の順を保ったまま切る（`n_a` は2〜3）。④は補足説明1つにつき1枚。

### 見出し画像（2026-10-28 決定）

- **参照するキャラクターシートは `キャラクターシート_MK-01〜MK-06` の6枚**（2026-10-30。旧 MC-01〜MC-04 から変更）。ポーズ・表情はこのシートをベースにして、記事ごとに変える（雛形の POSE AND EXPRESSION に明記）。

- 画像の文字は日本語だけだが、サブタイトルの `DayNNN` だけはラテン文字・数字を許可し、プロンプトに例外として明記する。
- 動物は描かせない（MC以外の人物・動物の禁止指定と矛盾するため、鳥などを足さない）。

## 7. 仕上げ

1. `python3 kaisetsu/check_kaisetsu.py`（NG 0件）。`python3 check_all.py` も通す。
2. 次の「PDCAの手順」を回す。
3. `README.md` の記事一覧に1行足す。コミットする（1記事または1作業ごと）。

## 8. PDCAの手順（記事を作るたびに必ず実行）

**P（計画）**：この記事の肢の中に、これまでの記事にない論点の型があるか（条文の取り違え、期間の起算日、申請人の範囲、条件の全部充足など）を確かめる。
**D（実行）**：上のルールで書く。
**C（点検）**：書き終えたら、次の問いに答える。
- 問題データ（`AM-NNN.json`）と、引用・まとめの正誤・正解番号が一致しているか（チェッカーが確認）。
- 初学者が、用語と場面を結びつけられるか。具体例は条文から外れていないか。
- 誤りの肢について、「問題文のどこが条文と違うか」が一文で言えているか。
- 補足説明は、混同しやすい肢に付いているか。図解は表・時系列・対比に落とせているか。
- 図解プロンプトの文言に、漢字リストの不整合・似た文字列の重複・番号の混入がないか。
- 書いている途中で手が止まった箇所、手直しした箇所はどこか。
**A（改善）**：見つかった改善点を、次の順で反映する。
1. 繰り返し起きうるものは、`check_kaisetsu.py` に検査を足す。
2. 書き方の指針になるものは、この「PDCAの手順」より上のルール（第3〜6節）に足す。
3. 雛形に関わるものは、`src/tpl.py` を直し、既存の記事を作り直して（`build_kaisetsu.py`）NG 0件を確かめる。
4. 反映した内容を、下の「改善記録」に日付つきで1行ずつ残す。改善点がなかったときも「改善点なし」と残す。
