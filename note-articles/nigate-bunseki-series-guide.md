# 苦手分析シリーズ note記事 執筆プロンプトと作業手順

`note-articles/column/nigate-NN-*.md`（苦手分析シリーズ）を新しく作るときの、固定の作業手順と、別チャットに貼って使える執筆依頼文をまとめる。⑦（意思表示の瑕疵、`column/nigate-07-ishihyouji-kashi-toikake-flow.md`）の制作過程で確立した。

## 1. シリーズの位置づけ

- 読者：「複数の年度で同じ論点を間違える」受験生。条文の網羅ではなく、**問題文を読んだあとに何を、どの順番で確認するか**を示す。
- 1問1答の年度別記事（`{年度}-mondai/`）とは別物。複数の年度の肢を、論点で横断して整理し直す。
- 既存：①敷地権制度の全体像／②分筆・合筆・合併・合体／③床面積算入の判定フロー／④相続放棄・代襲／⑤詐欺・強迫の第三者保護／⑥審査請求の制度／⑦意思表示の瑕疵。
- 新しい論点を決める前に、`ls note-articles/column/`と`grep -n "苦手分析シリーズ" note-articles/column/*.md`で、既存回と重なる範囲を確認する。重なる場合は、上位の整理か下位の掘り下げかを決め、記事の確認事項に関係を書く（⑦は⑤の上位。重なるのは第三者保護の結論だけ）。

## 2. 作業手順（この順で行う）

### 手順1　出題された年度と問をリストアップする

1. 対象の範囲を決める（⑦は民法の問1〜問3、R7〜H17の63問）。
2. `src/data/takuitsu.json`の問題文（`stem`・`alts`）は補助として使い、**年度別記事（`{年度}-mondai/q*.md`）を正とする**（⑧の作業で、DBの問題番号がずれている年度〈H28の「問1」が別の問題〉、肢の本文が欠けている問〈H29第2問、H24第3問は肢が要約のみ〉があると分かった）。DBの検索では、本文の空白を除いてから照合し、年度別記事の本文・まとめも「論点の用語」でgrepして両方で突き合わせる。問題文のデータを論点のキーワードで検索し、年度別記事（`{年度}-mondai/q*.md`）のまとめと突き合わせる。キーワードは、論点の用語と、それを言い換えた言葉の両方で探す（例：詐欺→「だまされ」「欺罔」）。検索で拾えない肢は、記事側を直接読む（⑦ではH24 第3問のオが問題文データの検索から漏れた）。
3. 次の4区分でリストにする。正解番号と、肢ごとの正誤・一言の論点を添える。
   - 主題の問（肢の大半が対象）／一部の肢に入っている問／周辺の論点として1〜2肢だけ出た問／似ているが範囲外にした問（範囲外にした理由を書く）
4. リストから言えること（何問中何問に、どの型の肢があるか）を数える。この数が、記事の山場（最も時間をかけるところ）を決める。⑦では「8問中6問に第三者の肢」「7問に強迫の肢」だった。

### 手順2　出題当時の法令と現行法の差を洗い出す

- **採用する肢の元記事の説明が、現行法に基づいているかを必ず点検する（⑧で追加）**。結論が変わらなくても、説明の根拠が旧判例・旧条文のままのことがある（⑧の作業で見つかった例：H28第1問ウは、元記事が旧判例の「裁判上の催告」で説明していたが、現行法は147条1項）。点検の結果は、記事の確認事項に年度ごとに書く。元記事に修正が必要なら、別作業としてユーザーに報告する。

- 年度ごとに、出題当時の法令と現行法の違いを書き出す（⑦：平成29年改正前は錯誤が無効、詐欺の第三者保護が善意のみ）。
- 記事は現行法で統一する。旧法の肢は、現行法で読み直しても結論が変わらないものを使う。変わる肢は取り上げないか、「出題当時は〜」の注を付ける（`format-template.md`の出題当時の扱いに従う）。
- 条文は`note-articles/laws/`の原文と照合する。未収録の条文だけe-Govで確認する。

### 手順3　問いかけのパターン（型）に分類する

- 肢の**最後の一文**（「〜できるか」「〜か」）で型を決める。型は3〜6個に収める。
- 型ごとに、肢数・該当する年度の肢・判定のカギ（誰の何を見るか）を書く。
- 「つまずきの構造」を1つ言葉にする。⑦では、取り消せること（当事者間）と第三者に対抗できること（第三者）を1つの問いとして処理してしまう点だった。これが記事の冒頭の「最初の一手」になる。

### 手順4　判定フロー（文章版）を作る

- 順序は「入口（型を決める）→ 制度・場面を見分ける → 型ごとの判定」とする。
- 各ノードに、根拠になる肢（年度・問・肢）を1つ以上ひもづける。ひもづく肢のないノードは書かない。
- 隠れた条件（⑦の錯誤：重過失のあと、相手方の認識と、相手方の同じ錯誤）は、1つのダイヤにまとめず別のダイヤにする。
- 覚え方（⑦：第三者の守られ方3段階）は、条文の明文の根拠ではない場合、そう明記する。

### 手順5　フローチャートを機械的に点検する（画像生成の前）

1. `note-articles/tools/flowchart_check_template.html`を使う。ノード（座標・種類・文言）と矢印を1つのデータで定義すると、図・経路の一覧・構造チェックが同じデータから出る。
2. Artifactとして公開するか、ローカルのブラウザで表示して、スクリーンショットで目視する。ヘッドレス表示は`/opt/pw-browsers/chromium --headless --no-sandbox --screenshot=...`で行える。
3. 点検する項目：
   - 全ダイヤに「はい」「いいえ」の出口がある（3分岐など例外は`multi`で明示する）。
   - 全ノードが開始から到達できる。結果ノードから矢印が出ていない。
   - 経路の数と、結果ノードの数。
   - ラベルが矢印や図形に重なっていない。文字が枠からはみ出していない。
4. 点検で見つかった不具合は、図ではなく**プロンプトの指示**として残す（手順6）。

### 手順6　図解プロンプトを作る

- 型は`infographic-prompt-template.md`の⑤作図ガイド型（フローチャート）と、③の早見表型を使い分ける。⑦は4枚（入口／当事者間／第三者／早見表）にした。
- 枚数は、1枚に載せるパネルが4つ以内で、縦の長さが約3000pxを超えない範囲で分ける。
- フローチャートのパネルには次を必ず書く。
  - 配置（縦の中心線、結果ノードはダイヤの右、左から右のレーン、など）。
  - ノード数・ダイヤ数・結果ノード数・経路数の合計。
  - 「はい／いいえ」を付けない分岐（3分岐など）は、付けないと明記する。
  - 矢印のつながらない図形（点線のダイヤなど）は、何にもつなげないと明記する。
  - 同じ文言の結果ノードは、別々のノードとして描くと明記する。
  - 長い結果ノードは、行数と、枠を広げて文字を内側に収める指示を書く。
  - 結果ノードの手前に60px以上の余白を取る（矢印のラベルが隠れる）。
- 1〜2字しか違わない文字列（例：善意／善意と無過失、取消しの前／取消しの後）は、「同一ではない」と明記し、色も変える（`infographic-prompt-template.md`の正誤対比の○×ルール4）。
- 「✓」「✕」の記号は使わず、結果ノードの文言と色で結論を示す（同じ箱に○と×を指示する矛盾を避ける）。
- 簡体字対策のFinal checkに挙げる漢字は、そのプロンプトに実際に出る字だけにする。書いたあと、本文との機械照合を行う（`infographic-prompt-template.md`の簡体字対策6）。

### 手順7　note本文を書く

構成（`column/nigate-05-*.md`・`nigate-07-*.md`を見本にする）：

1. タイトル：`## 【土地家屋調査士受験生向け】何度も同じところで間違える人へ〜苦手分析シリーズ{番号}{論点}〜`
2. `**対象条文：…**`（本文の根拠条文をすべて挙げる）
3. 導入（シリーズの紹介と、この記事で何をするか。専門用語は一度言い換える）
4. どの年度のどの問で出たか（手順1の区分別の一覧。箇条書き）
5. 最初の一手（手順3の型と、つまずきの構造）
6. 手順1、手順2…（手順4のフローを、確認する順に。各手順に「**たとえば**、」の具体例を1つ）
7. まとめ（箇条書き。表は使わない）＋迷ったときの確認順
8. 確認事項（条文の照合範囲、出題当時の法令の違い、条文の根拠がない整理はその旨、扱わなかった論点、既存回との関係、画像の生成状況）
9. 見出し画像用フレーズ（語り口調で5つ前後）
10. インフォグラフィック プロンプト（手順6の全画像）
11. 参考記事（リンク）

書き方の規則（`format-template.md`と共通）：

- です・ます調。全角括弧。表は使わない（noteで描画できない）。判例・先例・専門誌の番号は本文に書かない（確認事項に残す）。
- 条文番号は本文に書いてよい。条文の読み方の解説はしない。
- 年度別記事のように正解を伏せる必要はない（横断の整理なので、年度・問の正解番号は一覧に書いてよい）。
- 手順4で作ったフローと本文の順序を一致させる。

### 手順8　点検して保存する

1. 本文と図解プロンプトを照合する（文言・ノード数・経路数が一致しているか）。
2. `qa-checklist.md`のA（条文）、C（文章）、D（表の不使用）、F（体裁）を、本文に当てはめる。
3. 機械点検：コードフェンスの数が偶数か、フェンス内の英文に全角括弧が混じっていないか、Markdown表（`|`で始まる行）がないか、Final checkの漢字リストが本文に実在するか。
4. `main`ブランチに保存してコミットする（`CLAUDE.md`の運用ルール。作業セッションごとにコミット、pushの前に`git pull origin main`か`git fetch`＋`git rebase origin/main`）。
5. 画像は生成しない。画像生成はChatGPTで行い、生成後は、手順5のページの経路の一覧と突き合わせて確かめる。

## 3. 別チャットに貼る執筆依頼文（{　}を差し替える）

```
土地家屋調査士試験のnote解説記事「苦手分析シリーズ{番号}」を作ってください。
論点は「{論点}」、対象は{範囲（例：R7〜H17の択一式 問1〜問3）}です。

作業手順は note-articles/nigate-bunseki-series-guide.md の手順1〜8に従ってください。
先に CLAUDE.md、note-articles/format-template.md、infographic-prompt-template.md、
qa-checklist.md、note-articles/column/ の既存の苦手分析シリーズ（nigate-05、nigate-07）を読んでください。

進め方：
1. まず手順1〜3（出題年度と問のリスト、出題当時の法令と現行法の差、問いかけの型）まで作って、
   私に見せてください。
2. 承認後、手順4〜6（判定フロー、フローチャートの機械点検、図解プロンプト）に進んでください。
   フローチャートは、note-articles/tools/flowchart_check_template.html を使って
   ノードと矢印を点検してから、プロンプトに配置・ノード数・経路数を書いてください。
3. その後、手順7〜8（note本文、点検、保存）に進んでください。

保存先は main の note-articles/column/nigate-{番号}-{英字のslug}.md です。
```

## 4. ⑦の制作で見つかった不具合と、手順に入れた対策（実績）

- 問題文データの検索で拾えない肢があった（H24 第3問）→ 手順1：記事側も直接読む。
- 取り消せること（当事者間）と第三者に対抗できることを混同する誤答が多い → 手順3：つまずきの構造を冒頭に置く。
- 錯誤の「相手方の認識」と「相手方の同じ錯誤」を1つのダイヤにまとめる危険 → 手順4・6：別のダイヤにし、プロンプトにも明記。
- 点検用の図でラベルが矢印に重なる、結果ノードが近すぎて「はい」が隠れる、3行のノードの文字が枠からはみ出す → 手順6：余白と枠の幅の指示。
- 「はい・いいえ」でなく3分岐の図を、2分岐に描き直される恐れ → 手順6：分岐が3本でラベルを付けないと明記。
- 矢印につながない点線のダイヤが、図の流れにつながれる恐れ → 手順6：何にもつなげないと明記。
- 近い文字列（善意／善意と無過失）が同じ文字列に複製される恐れ → 手順6：同一ではないと明記し、色も変える。
- Final checkの漢字リストが本文とずれた（実在しない字を挙げた、実在する字が漏れた）→ 手順6：本文との機械照合。
