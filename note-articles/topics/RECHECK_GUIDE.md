# 個別テーマ記事の再チェック指示（`topics/`）

作成 2026-11-05。`topics/` の個別テーマ記事（KA〜KT）を1本ずつ再チェックし、あわせて note の見出し画像のプロンプトを新しく作って記事に追加するときの手順。
実施の見本は `KA_01_hyoudaibu-shoyuusha-vs-toukimeigijin.md`（2026-11-05）。

依頼文の例：「`note-articles/topics/RECHECK_GUIDE.md` に従って、{ID}（複数可）を再チェックしてください」

## 守ること

- 作業は `main` に直接コミット・push する（CLAUDE.md）。セッションで別の作業ブランチを指定されているときは、同じコミットをそのブランチにも push する。
- 作業の前に `git pull origin main`。1記事ごとにコミットする。
- 記事に書く法的内容は、必ず `note-articles/laws/` の原文で確かめる（記憶で書かない）。確かめきれない点は断定せず、確認事項に書く。
- 作業中に新しい種類の誤りや手戻りを見つけたら、F の手順で改善記録に残し、有効なものを指示書に足す。
- 画像は生成しない。生成と目視確認はユーザーがChatGPTで行うので、「未実施」と明記する。
- 個人の演習結果（誤答の回数・自分の回答）と、分析の根拠にした問題番号の列記は、記事にも画像の文言にも入れない。
- 年度・問は算用数字で書く。禁止語（決定木・ツリー・判定木）は使わない。

## A. 記事本文のチェック

1. **条文の照合**：記事中の条文番号・項・号・文言を `laws/` の原文と一つずつ照らす（法・令・規則・準則・区分所有法など）。引用が原文どおりか、号数のずれがないか。
2. **関連する過去問記事との整合**：記事が参照している過去問記事（`r?-mondai/` など）の結論と食い違わないか。
3. **説明不足・誤解を招く表現**：条文の誤りだけでなく、読者が誤って理解しやすい表現を探す。
   - 試験でよく問われる条文（申請適格、手続の順序、例外）が抜けていないか。
   - 「〜が多い」など、根拠のない一般論になっていないか（確認できる言い方にやわらげる）。
4. **本文内の整合**：見出し・本文・具体例・まとめの箇条書きが互いに矛盾していないか。
5. **体裁**：次の順になっているか確認する。
   - タイトルは `## 【土地家屋調査士】{ID}_{題名}` の形に統一する（2026-11-05 ユーザー指示。例：`## 【土地家屋調査士】KA_01_「表題部所有者」と…`）。
   - タイトル、対象条文、導入文、見出しごとの解説、まとめ、確認事項、見出し画像用フレーズ、見出し画像プロンプト、インフォグラフィックのプロンプト、関連記事・参照した過去問。
   - 作業メモ（「このまま使える点…」など）が残っていれば「確認事項」に直す。
   - 「正解の先出し」は、過去問に紐づく記事だけで気にする。
6. **確認事項ブロック**：条文で確かめた根拠と、確かめきれなかった根拠を分けて正直に書く。

## B. 図解（インフォグラフィック）のチェックと追加

`note-articles/infographic-prompt-template.md` の③と、同ファイルの「図解プロンプトと記事本文の整合チェック」に従う。

1. **既存プロンプトを本文と照合する**：数字・割合・要件・当事者の役割・登記や手続の名称が本文どおりか。本文を直したら、図解も同じ内容に直す。
2. **流れ図の作りを確かめる**
   - 実際に判断する流れになっているか（一直線に並べただけでないか）。
   - 「いいえ」側にも専用の行き先があるか。戻る矢印がないか。
   - 結論に影響しない事実を分岐にしていないか（点線の札で「問わない」と示す）。
   - 同じ意味の判断が重複していないか。
   - 配色は、はい＝青、いいえ＝赤で統一されているか。
3. **足りない図を足す**：本文で説明しているのに図がない論点を洗い出し、型（俯瞰カード・対比表・早見表・判定フロー・段階フロー）を選んで追加する。枚数の上限はない。
4. **必須文言の確認**：簡体字・繁体字の禁止、絵の中の文字は指定した語だけ、番号を付けない、背景は不透明、Final check。
5. **画像に入れてよい数字は、年度・問の数字だけ**。条文番号は画像に入れず、記事に書く（フッターにも入れない）。
6. **note用とInstagram用の2種類**：Instagram用は4:5（1080×1350）に固定で、余白は左右54px・上下68px。アカウント名・URL・ハッシュタグ・「noteへ」などは入れない。問題番号は画像に入れない。
   - 総論の4:5は `instagram/<ID>_zukai_4x5.md`、追加分は `instagram/<ID>_zukai_4x5_extra.md` に置く。

## C. note の見出し画像のプロンプトを追加する（全記事）

すべての個別テーマ記事に、note用の見出し画像（アイキャッチ）のプロンプトを新しく作って追加する。すでにある場合は、この仕様で作り直す（古い「藍子だけ」の記述〈KC_02 など〉は置き換える）。

### 仕様
- **サイズ**：1280×670px（1.91:1・横長）。noteの一覧では上下が切れるので、タイトルとキャラクターは中央付近に置く。
- **キャラクター**：MC（女性）1人だけ。トリ先生・藍子は描かない。基準はキャラクターシート `キャラクターシート_MC-01〜MC-04` の4枚で、ChatGPTに添付してから貼る。ポーズは固定せず、毎回変えてよい。手と腕の数など、人体を正しく描くよう指示する。
- **画風**：水彩風、淡くやわらかい描写。同じシリーズの見出し画像と揃える。
- **背景（2026-11-05 ユーザー指示で変更）**：壮麗な図書館の館内。高い本棚、石造りのアーチ窓、木を使った重厚な内装、装飾のある天井、柔らかな暖色の照明。奥行きがあり、明るく上品な印象にする（暗く重くしない）。タイトルの背後は明るくすっきりさせる。
- **文字**：タイトル2行＋サブタイトルの帯の、合計3行を基本とする。
  - 1行目：濃紺（淡黄色のマーカー風）。2行目：大きく、強調する語を赤橙、残りを濃紺。サブタイトルは水色の丸い帯に濃紺。
  - 文字は記事の見出しを短くしたもので、1字ずつ表にして確かめる。
  - 数字・英字・簡体字・繁体字は入れない。年度・問の数字を入れるのは過去問に紐づく記事だけで、個別テーマ記事では数字を入れない。
- **左右の背景**：図書館の内装だけを描く。人物・動物・テーマを説明する小物・机上の物・アイコン・図解は入れない。左右の本棚や窓は、タイトルとキャラクターより目立たせない。物の上には文字を書かせない。フローチャート・矢印・○×は描かない。
- **背景**：不透明（透明背景・市松模様の禁止）。
- 書式の見本は `note-articles/topics/zukai-kikaku/header-image-prompts.md` の「note用（1280×670）」ブロック。

### 手順
1. 記事の主題から、画像の文字（1行目・2行目・強調語・サブタイトル）を決める。強調語は2行目の中の連続した語にする。絵（`scene`）は見出し画像には使わない（背景は図書館で固定）。
2. Instagram用の見出し画像（`instagram/data.json` の `l1`・`l2`・`emph`・`band`・`scene`）がある記事は、その文字を土台にしてよい。note用はサブタイトル（`band`）を記事の主題に合わせる。4行目（`sub`）は note用では入れない。
3. `## 見出し画像プロンプト（note用・1280×670）` の節を、`## インフォグラフィック プロンプト` の直前（図1の上）に置く（それがない記事は「見出し画像用フレーズ」の直前）。節には、文字の表、A（新規に生成）、B（元の見出し画像の背景だけを差し替える）の2つのコードブロックを入れる。
   - 全記事分は `python3 note-articles/topics/gen_note_header.py` で作り直す（`instagram/data.json` の `l1`・`l2`・`emph`・`band` から作る。何度実行しても同じ結果になる）。記事ごとに文字を変えるときは `data.json` を直す。生成物は手で直さない。
4. 文字の表の下に、確かめることを書く：大きさ、1字ずつの一致、MC1人だけ、手や腕の数、背景が不透明。
5. 文字が崩れるときは、「TEXT」を「No text」に書き換えて文字なしで作らせ、文字はCanvaなどで重ねる。直すときは、最後に「次の点だけを直して、ほかは変えない：…」と1文足す。

## D. Instagram用ファイルの更新

- 本文の修正（結論・要件・用語）に合わせて `instagram/data.json` を直す。見出し画像の文字は、本文と矛盾しなければ変えない。
- `python3 note-articles/topics/instagram/gen_instagram.py` で `instagram/<ID>.md` と `README.md` を作り直す（生成物は手で直さない）。
- 箇条書き（`points`）の個数に上限はない（2026-11-05 ユーザー指示で撤廃）。キャプションが2200字を超えるときは、個数を減らさず、各項目の文を短くして調整する。
- `python3 note-articles/topics/instagram/check.py` で NG 0 件にする。

## E. 仕上げと報告

1. 変更を1記事ごとにコミットし、`main` に push する（指定ブランチがあればそこにも）。
2. 報告に次を書く：
   - 見つけた誤り・不足と、直した点。
   - 未解決の点（条文だけでは言い切れない論点）。
   - 追加した図解の枚数と型。
   - 追加した見出し画像プロンプト。
   - 「画像の生成と目視確認は未実施」の一文。
   - 新しく見つけた種類の問題と、指示書に足した項目（F の改善記録の追記分）。

## 一括で進めるとき

- 全51本は一度にやらず、棚（KA、KC、KD…）ごと、または10本前後ずつに分け、1記事ずつコミットする。
- 進み具合は `topics/README.md` に「再チェック済み／見出し画像プロンプト済み」の表で残す（未記入のIDは未実施）。
- 並列に進めるとき（Agent）は、1エージェントに1記事を渡し、依頼にはこのファイルのパスと対象ID、`laws/` の場所を明記する。法令の照合は各エージェントが自分で行い、他の結果を信じて省略しない。

## F. 修正作業のPDCA（新しい修正事例が見つかったとき）

再チェックの途中で、この指示書のチェック項目に載っていない種類の誤り・不足・手戻りが見つかったら、その場で対処したうえで、次の順に回す。**対処の履歴（下の改善記録）をもとに、有効なものだけをこの指示書の本文に足す。**

### Plan（見つけたときに記録する）
- 何が見つかったか（記事ID・箇所・内容）を1行で書く。
- 既存のチェック項目（A〜E）で拾えたはずのものか、新しい種類かを分ける。拾えたはずのものは、項目の書き方が弱いので、その項目を具体的に直す。

### Do（対処する）
- 記事・図解・Instagram用ファイルを直す。同じ種類の問題が他の記事にもないかを、手元の別記事で1〜2本だけ見て確かめる（全部は調べない）。
- 直した内容を、下の「改善記録」に追記する（日付・記事ID・見つけたこと・対処・原因）。

### Check（有効かどうかを判定する）
次の3つのすべてに当てはまるものだけを「有効」とする。
1. **再現性**：別の記事でも起こりうる（その記事だけの個別の事情ではない）。
2. **確認可能**：チェック項目として「何を・どこで・どう確かめるか」を一文で書ける。
3. **重複なし**：A〜Eの既存項目に含まれていない（含まれるなら、その項目を具体化する）。

個別の事情だけのものは、改善記録に残すだけにして、本文には足さない。2本以上の記事で同じ種類が見つかったものは、優先して本文に足す。

### Act（指示書に反映する）
- 有効なものは、A〜Eの該当する節に、理由つきで一項目として足す（理由は「改善記録」の日付を添える）。
- 反映したら、改善記録の該当行に「反映済み（節・項目）」と書く。
- 指示書を直したときは、`topics/README.md` の「再チェック済み」の表の備考に、新しい項目を適用した記事とまだの記事が分かるようにしておく（まだの記事は、次に触れるときに新しい項目で見直す）。
- 規則を足すときは、すでにある規則と矛盾しないか、他の指示書（`infographic-prompt-template.md`、`CLAUDE.md`）と食い違わないかを確かめる。食い違うときは、勝手に上書きせずユーザーに確認する。
